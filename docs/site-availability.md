# Проверка доступности сайта

## Результаты 5 сентября 2026 года

- Локальный DNS и Google DNS возвращают для `skazkids.ru` адрес `201.34.140.220`.
- Google DNS не возвращает запись AAAA: неисправный IPv6 в DNS этой проверкой не обнаружен.
- При активном WireGuard `https://skazkids.ru` отвечает `200`, `/api/health` — `{"status":"ok"}`. Это разовая проверка, а не подтверждение постоянной доступности.
- `http://www.skazkids.ru` закрывает соединение без HTTP-ответа. В исходном конфиге этот домен попадал в сервер по умолчанию с `return 444`.
- `https://www.skazkids.ru` не проходит проверку имени в сертификате. Перенаправление по HTTPS возможно только после успешной проверки сертификата.
- Кириллический домен `xn--80aiiehc9bg.xn--p1ai` отвечает перенаправлением `301` на основной адрес.
- Попытка привязать запрос к физическому Wi-Fi при активном VPN отклонена Windows до установления TCP-соединения. Она не доказывает блокировку сайта оператором.
- SSH-вход `root@201.34.140.220` имеющимся локальным ключом отклонён: `Permission denied (publickey)`. Состояние служб и серверные журналы не проверены; изменения на сервер не установлены.

Ошибка `www` подтверждена отдельно. Она не объясняет сбои адреса без `www`, если пользователь открывает именно его. Возможные причины таких сбоев — фильтрация или маршрутизация до IP, правила сетевого экрана и нестабильность сервера; подтверждения конкретной причины пока нет.

## Применение исправления www на VPS

Не устанавливать новую HTTPS-конфигурацию до расширения сертификата.

1. Через рабочий SSH-доступ проверить `nginx -T` и `certbot certificates`. Определить действующий файл сайта и все имена в сертификате `skazkids.ru`. Сохранить резервную копию этого файла перед изменениями.
2. В действующем HTTP-блоке основного домена добавить `www.skazkids.ru` к `server_name`. Проверить `nginx -t`; только при успешной проверке выполнить `systemctl reload nginx`.
3. Расширить сертификат через установленный плагин Certbot Nginx. Следующая команда применима, если текущий сертификат содержит только основной и указанный кириллический домены. Если есть другие имена, сохранить их, добавив отдельные аргументы `-d`.

   ```sh
   certbot certonly --nginx --cert-name skazkids.ru --expand -d skazkids.ru -d xn--80aiiehc9bg.xn--p1ai -d www.skazkids.ru
   ```

4. Проверить успешный выпуск и наличие всех имён через `certbot certificates`. При ошибке остановиться: не устанавливать HTTPS-блок `www` с прежним сертификатом.
5. Перенести блоки `www` из `deploy/nginx-skazkids.conf` в действующий конфиг, сохранив другие настройки сервера. Выполнить `nginx -t`; только при успехе — `systemctl reload nginx`.
6. Проверить оба адреса `www` с путём и параметрами: они должны возвращать `301` на `https://skazkids.ru/путь?параметры`, без ошибки сертификата. Основной адрес должен отвечать `200`.
7. Проверить автоматическое продление: `certbot renew --dry-run`.

При ошибке проверки Nginx не перезагружать службу. Восстановить резервную копию, повторить `nginx -t` и только после успешной проверки выполнить перезагрузку конфигурации.

## Диагностика основного домена

На одном устройстве выполнить команды сначала с выключенным VPN, затем с включённым. Зафиксировать время и текст ошибки. В Windows использовать `curl.exe` вместо `curl`.

```sh
curl -I --connect-timeout 10 --max-time 20 https://skazkids.ru
curl -I --resolve skazkids.ru:443:201.34.140.220 --connect-timeout 10 --max-time 20 https://skazkids.ru
curl --connect-timeout 10 --max-time 20 https://skazkids.ru/api/health
```

`--resolve` исключает DNS из проверки, сохраняя проверку HTTPS-сертификата. Не использовать `-k`.

На VPS в те же минуты проверить:

```sh
systemctl status nginx skazkids postgresql --no-pager
journalctl -u skazkids --since '30 minutes ago' --no-pager
journalctl -k --since '30 minutes ago' --no-pager
free -m
df -h /
curl --connect-timeout 5 --max-time 10 http://127.0.0.1:3000/api/health
```

Пути журналов Nginx взять из действующего `nginx -T`. Не публиковать сырые журналы: они могут содержать адреса и пользовательские данные.

Если запрос с фиксированным IP не устанавливает TCP-соединение без VPN, а через VPN проходит, проверять маршрут, фильтрацию и сетевой экран. Если TCP устанавливается, но не проходит TLS, проверять сертификат и TLS-соединение. При `502/504` сопоставить время запроса с журналами Nginx и приложения. Если основной HTML возвращается успешно, проверить загрузку CSS, JavaScript и изображений в браузере.
